## Findings by area

### Resource lifecycle

- [chat-backend/app/main.py:174](../../chat-backend/app/main.py#L174) [medium]: lifespan shutdown awaits `db.close()` without draining `app.state.shout_notify_tasks`; an in-flight `_notify_queue` runs `db.shout_pending_count()` against a closing pool. The task set exists specifically so a digest cannot vanish mid-send (its comment says so), and shutdown is the one path where it still can.
- [src/components/experience/Goat.astro:266](../../src/components/experience/Goat.astro#L266) [low]: bleat-removal `setTimeout` handle is never stored; the disposer removes the listener only, so navigating within 650ms of a tap leaves a timer holding a detached element.
- [src/lib/home/commitPopups.ts:110](../../src/lib/home/commitPopups.ts#L110) [low]: per-popup `setTimeout` handles untracked; `dispose()` detaches the container but leaves timers pending until they fire.

### Data integrity

- [chat-backend/app/chunking.py:26](../../chat-backend/app/chunking.py#L26) [medium]: `_TOKENS_PER_WORD = 1.4` is calibrated on English prose ("English BPE runs ~1.3 tokens/word") but `chunk_code` applies it to source, where one whitespace-word such as `self._model.embed(list(texts))` is many BPE tokens, not 1.4. A code chunk estimated under the 480 cap can still exceed the embedder's real 512 ceiling and be truncated silently. Noted honestly: the module docstring already claims the estimate "holds well under 512 real tokens even for token-dense text", so this is a disagreement with a stated assumption, and it is empirically settleable by tokenising the largest existing code chunks.
- [chat-backend/app/request_log.py:114](../../chat-backend/app/request_log.py#L114) [low]: `query`/`response` truncated with no marker, so a reader cannot distinguish an answer that was exactly the cap from one the logger cut.

### Concurrency

- [chat-backend/app/main.py:379](../../chat-backend/app/main.py#L379) [high]: TOCTOU on the shoutbox gate. `shout_pending_count()` and `shout_duplicate_exists()` are separate awaits, then `enqueue_shout()` is a third, with no transaction. `body_hash` is indexed but deliberately **not** UNIQUE (`sql/005_shoutbox.sql:48` explains why: the same text is legitimately allowed again after the window). Two concurrent identical submissions can both read `duplicate_exists=False` and both insert, bypassing the gate on a public write endpoint. The absence of the constraint is intentional, so the fix is not simply adding UNIQUE.
- [chat-backend/app/retrieval.py:329](../../chat-backend/app/retrieval.py#L329) [medium]: `async def retrieve()` calls the synchronous, CPU-bound `Embedder.embed_query` (ONNX inference) directly, with no executor. On a single-process event loop this stalls every concurrent SSE stream's token flush, every `/health` probe, and rate-limiter timing for the duration of the embed.
- [chat-backend/app/retrieval.py:527](../../chat-backend/app/retrieval.py#L527) [medium]: same blocking embed on the progressive-disclosure expansion path.
- [chat-backend/app/main.py:381](../../chat-backend/app/main.py#L381) [medium]: the same check-then-act window lets concurrent requests each observe `pending_total < QUEUE_MAX_PENDING` before any insert lands, so the 200-item backpressure cap can overshoot.
- [chat-backend/app/main.py:227](../../chat-backend/app/main.py#L227) [low]: `prune_counter` incremented across `await call_next(request)`; lost updates can delay the amortised prune sweep. The code's own comment calls this harmless, and it is, but it is a genuine unsynchronised read-modify-write across an await.

### Error paths

- [chat-backend/app/pipeline.py:518](../../chat-backend/app/pipeline.py#L518) [high]: the outer `try` wrapping the streaming block has a `finally` (semaphore release) at line 689 and **no `except`**. The two other try blocks in the same file (127, 343) both have one. If `to_source_refs` or `build_messages` raises here, the generator propagates uncaught, `StreamingResponse` closes mid-stream with no `sse_error` or `sse_done` frame, and no `log_request` records it. That hanging-stream outcome is the exact failure the rest of this file is built to prevent.
- [chat-backend/app/request_log.py:196](../../chat-backend/app/request_log.py#L196) [low]: `except Exception: pass` with no logging, unlike the sibling degrade path at 152 which warns. A bug inside `format_log_record` would kill the request log permanently and silently.
- [chat-backend/ragctl.py:180](../../chat-backend/ragctl.py#L180) [low]: `http_json` returns `None` for both "unreachable" and "reachable but malformed", so health and usage probes cannot tell down from broken. Contrast `_healthy_http` below it, where the broad catch is documented as deliberate.

## Refuted on verification

Recorded rather than deleted: a rejected finding with its evidence is worth more
next run than one that quietly disappears.

- **`CORS_ALLOW_ORIGINS` defaults to `*`** (raised against `chat-backend/.env.example:99`, `docker-compose.yml:91`, `chat-backend/app/main.py:236`), severity medium, claiming any origin can drive the funnel-exposed backend. Refuted twice over. First, `allow_credentials` is not set and defaults off, and the comment directly above the cited middleware states the reasoning: with no credentials there is nothing for a cross-origin caller to ride, and the API has no auth to abuse. Second, production does not use the default at all: the live `.env` sets `CORS_ALLOW_ORIGINS=https://mikkonumminen-dev.vercel.app`, confirmed both in the file and in the running container's resolved environment. The subagent read the example and the compose default and never checked what the deployment resolved.
