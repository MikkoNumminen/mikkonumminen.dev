# AudiobookMaker: Engineering Deep-Dive

This document covers the specific hard problems encountered while building AudiobookMaker and how they were solved. It assumes familiarity with the stack (see the architecture doc for the overview) and focuses on bugs, war stories, and the reasoning behind non-obvious choices.

## PDF Extraction: The Invisible-Character Problem

PyMuPDF extracts text faithfully, but faithfully includes every formatting artifact embedded in the source PDF: non-breaking spaces (U+00A0), zero-width joiners (U+200D), zero-width spaces (U+200B), Ogham space marks, Unicode line separators (U+2028), and the entire Zs category of Unicode space separators. Most TTS engines either skip these silently or, worse, read out the Unicode codepoint name. The chunker also splits incorrectly on zero-width characters that appear inside words.

The fix, added to `pdf_parser.py` as `_normalize_unicode_whitespace`, runs first in the `clean_text` pipeline: a compiled regex strips zero-width characters entirely, maps Unicode line and paragraph separators to real newlines so downstream paragraph-break logic applies to them, and collapses all Zs-category spaces to ASCII space. Soft hyphens (U+00AD) are a separate case. They are typographic line-wrap hints that look like nothing in a reader but appear as literal hyphen characters in extracted text. They have to be stripped with the hyphenation logic, not the whitespace pass, because the correct treatment depends on whether a newline follows (word-wrap reconstruction) or not (standalone soft hyphen, just drop it).

The hyphenation logic itself has a three-way split. A hard hyphen at end of line followed by a lowercase letter is a word split across a line break and gets rejoined without the hyphen. The same followed by an uppercase letter or digit is a genuine compound word (e.g. "1200-luvulla" split across a line) and gets rejoined with the hyphen preserved. Soft hyphens are stripped regardless. Without this specificity, Finnish compound words like "1200-luvulla" were silently merged with their successor text.

Chapter heading detection is similarly cautious. A regex matches numbered headings ("Luku 3", "Chapter 4", "3. Title") plus Roman-numeral headings, but the numeric prefix is capped at three digits specifically to avoid mistaking years ("1500.") for chapter markers. A separate length cap (80 characters) rejects any line too long to plausibly be a title. A lookahead check (more than four words after the first internal period) rejects prose sentences that happen to start with a number. The fallback for documents with no detected headings treats the entire book as one chapter rather than producing an empty output.

## OCR Fallback: The tessdata/configs Trap

When any page returns empty text from PyMuPDF, the parser automatically runs ocrmypdf (wrapping Tesseract + Ghostscript) on the whole document and re-extracts. The trigger is per-page, the OCR is document-wide, and `skip_text=True` means mixed PDFs (a scanned cover image plus a born-digital body) only incur Tesseract on the pages that actually need it.

The cache key is a SHA-256 hash of the source file's bytes, not its name or mtime. A renamed copy of the same scanned PDF hits the cache; any byte change misses. The first cold OCR of a 32-page document takes roughly 25 seconds; cache hits are under 100 ms.

The silent killer during development was `tessdata/configs/`. Without that subdirectory, ocrmypdf completes 100% of OCR work, then crashes trying to parse empty hOCR output. The failure looks like an OCR crash, not a missing-config crash. The fix required an extra glob in the PyInstaller spec to copy the configs subdirectory alongside the tessdata `.traineddata` files, and a CI smoke test against a real 32-page scanned document to gate against any regression. Both `eng.traineddata` and `fin.traineddata` are SHA-256-pinned in the build workflow against the tessdata_fast 4.1.0 tag.

A partial OCR output file from a crashed run is deleted by the exception handler in `_run_ocr_fallback` before returning `None`. Without that cleanup, the next run would find a zero-byte or truncated PDF at the cache path, treat it as a valid cache hit, and fail forever.

## Chunking: When Neural TTS Meets Tiny Inputs

The chunker in `tts_chunking.py` splits on sentence boundaries first, then clause boundaries (commas, semicolons, colons, dashes), and only falls back to word boundaries as a last resort. The clause-boundary preference is deliberate: each chunk boundary introduces an audible pause in the assembled audio, so breaking at a place the listener already expects a pause is better than breaking mid-phrase.

The abbreviation table matters more than it looks. A period after "esim", "ks", "tri", "Dr", "Vol", or "p" is not a sentence boundary: the chunker has an explicit set of 30-odd Finnish and English abbreviations that must not trigger a sentence split. Single-letter initials (like "H. Pihlajamäki") are also excluded. A lookahead checks that a period is followed by whitespace and then an uppercase letter before committing to a sentence break; "google.com" or "5.2" never trigger it.

The more subtle bug is tiny chunks. When a long sentence is force-split at clause boundaries, the last clause fragment is sometimes 7–15 characters (something like "vuoksi,". Neural TTS models (Chatterbox specifically) exhibit pathological behavior on inputs this short: the model rambles for 10+ seconds, producing garbage audio that passes VAD-based silence detection and ends up in the assembled book. The fix is `_merge_short_chunks`, which the Chatterbox runner opts into by setting `min_chars`. Any chunk shorter than `min_chars` is folded into the preceding chunk, allowing modest overflow past the maximum chunk size) a 230-character chunk sounds fine; a 7-character one does not. The same issue appeared in v3.15.3 as the "floor-aware band guard": the truncation detector was checking for catastrophic drops (a near-zero-duration output), but missing partial truncations where a sentence lost a third of its words. The fix derived thresholds from measured healthy-chunk audio distributions rather than guessing.

The chunk cache (`bad cached chunks are re-synthesized`, v3.15.3) adds a second defense: on a resumed conversion, each cached chunk is validated before being accepted. A cached chunk that fails health checks is re-synthesized rather than shipped.

## The Chatterbox Venv: An Isolation Problem in Five Acts

The Chatterbox engine's PyTorch and CUDA dependencies (~15 GB of model weights) live in a separate Python 3.11 venv. This keeps the main app bundle below 200 MB and prevents dependency conflicts. But the isolation boundary turned out to be leaky in several ways, each discovered through field failures.

**Act 1 (v3.17.2): PYTHONPATH pollution.** The frozen PyInstaller app sets `PYTHONPATH` to point at its bundled packages. When the Chatterbox subprocess launched using `os.environ`, it inherited that `PYTHONPATH`, which caused the venv's Python interpreter to prefer the app's bundled packages over its own site-packages. Model load failed with "Could not import module 'LlamaModel'" even though the venv was healthy. The fix in `isolated_python_env()` strips `PYTHONPATH`, `PYTHONHOME`, and `PYTHONSTARTUP` and sets `PYTHONNOUSERSITE=1` before spawning. The same environment is used for both synthesis runs and the post-install smoke test, so the verified environment and the synthesis environment cannot diverge.

**Act 2 (v3.17.0): The half-built venv.** If the user started a synthesis during or immediately after an install, the runner could launch against a venv that was still being constructed. The venv now carries an `.install-incomplete` sentinel file from the moment of creation until the post-install smoke test passes. While that file exists, the engine reads as not-installed and Convert is blocked. Repair can then distinguish a corruption-shaped smoke failure (missing DLLs, import errors (triggers a clean delete-and-rebuild) from an environmental failure (no NVIDIA driver) surfaced as a direct error, no rebuild).

**Act 3 (v3.17.1): Repair downgraded CUDA torch.** The v3.16.0 Repair button ran `pip install --force-reinstall` on the dependency list, which let pip re-resolve and pull the CPU-only torch wheel from PyPI instead of the CUDA-pinned wheel. Post-repair synthesis failed with "Torch not compiled with CUDA enabled". The fix pins the torch install to the exact cu124 wheel URL without touching it during repair. A self-healing path also detects an already-degraded non-CUDA build in the venv and reinstalls the correct wheel in place.

**Act 4 (v3.17.3): The smoke test that couldn't lie.** The post-install test previously called a lightweight check script that imported modules but didn't exercise the actual synthesis path. The result was a venv that passed "Moottorit asennettu" (engines installed), while the real synthesis runner (which imports different modules in a different order) still crashed. The fix runs a `--selftest` flag on the same runner script the production path uses, through the same `isolated_python_env()` call. A stale runner script (from a previous app version) is now visible in logs via a build stamp printed at the top of every run.

**Act 5 (macOS path-root bug):** `engine_installer._allowed_venv_roots()` whitelisted `TEMP` and `TMP` (Windows env var names) but not `TMPDIR` (the macOS and Linux equivalent). The path-validation check therefore rejected `tmp_path` fixtures on the developer's Mac while Windows CI stayed green. The fix adds `TMPDIR` to the whitelist and adds a macOS CI leg (`tests-macos.yml`) to catch any future platform-specific regressions.

## The Waiter Thread That Killed Long Books

`ChatterboxRunner` spawns two daemon threads: a reader that parses the subprocess's stdout line by line, and a waiter that calls `proc.wait()` and queues an exit event when the process finishes. The waiter originally applied a 60-second timeout to `proc.wait()` unconditionally, then escalated to terminate/kill. This killed any synthesis longer than 60 seconds mid-flight and reliably aborted the final MP3 assembly phase on books with 200+ chunks (assembly prints nothing while it runs and legitimately takes minutes).

The fix separates the cancel path from the normal-completion path via a `cancel_requested` threading.Event. A normal run calls `proc.wait(timeout=1s)` in a polling loop with no upper bound on the loop count. Only after a user cancellation (or the 12-hour absolute ceiling for a wedged process) does the escalation budget (60-second grace, then terminate, then kill) apply. The same bug caused the reader thread's exception to silently kill it: an `OSError` mid-readline would leave the event queue empty and the GUI's poll loop spinning on `finished == False` forever. The reader now wraps its main loop in a broad try/except that stashes any exception for `join()` to surface and pushes a synthetic error event so the UI loop sees something.

## Upstream Chatterbox: Two Bugs Requiring In-Process Patches

AudiobookMaker's multi-chunk synthesis loop exposed two upstream bugs in the Chatterbox library that made it unusable for audiobook-length work.

**The hook leak.** `AlignmentStreamAnalyzer.__init__` calls `register_forward_hook` and discards the returned `RemovableHandle`. Three hooks are registered per call (one per entry in `LLAMA_ALIGNED_HEADS`). Because a new analyzer is constructed on every `T3.inference()` call, after N calls the attention layers carry 3N stale hooks, all still firing on every forward pass. The stale hooks corrupt the alignment matrix fed to `AlignmentStreamAnalyzer.step()`, tripping the `long_tail` / `alignment_repetition` heuristics and forcing EOS almost immediately. Call 1 returns ~18 seconds of audio; calls 2-5 return ~0.4 seconds of garbage. The prepared fix (`docs/upstream/chatterbox/hook_leak_fix.patch`) adds `self._hook_handles` to store every `RemovableHandle`, saves the two `tfmr.config` mutation fields exactly once (guarded by `self._config_patched` so repeated construction cannot overwrite the true originals with already-patched values), adds `AlignmentStreamAnalyzer.close()` for context-manager use, and wraps the generation body in `try/finally` inside `T3.inference()` so hooks are always removed even on exception. AudiobookMaker currently works around the leak by clearing `_forward_hooks` directly before each call: the patch targets the upstream library for the benefit of any multi-chunk workflow.

**The flow token crash.** `chatterbox/models/s3gen/flow.py::inference()` detects out-of-range speech tokens (logging "out-of-range special tokens found in flow, fix inputs!") but then passes them unclamped to `nn.Embedding`. An index above `vocab_size` is an out-of-bounds read on the CUDA side, triggering a device-side assert that terminates the entire synthesis process mid-book. The sibling `forward()` already clamped `min=0`; the fix clamps both ends in `inference()` so a single bad T3 token degrades one audio frame instead of aborting a multi-hour run. The patch is applied at install time by `engine_installer._patch_flow_token_clamp()` and self-healed at runner startup for venvs that were already present before the fix shipped. Both bugs surface only in multi-call synthesis loops; single-call use (which is how most upstream testing is done) never triggers them.

## Audio Assembly: Memory and Format Fidelity

The original assembly path loaded all synthesized chunks into a single pydub `AudioSegment` and concatenated them in memory. An 8-hour audiobook allocated roughly 2.5 GB of PCM transiently. The replacement path writes each trimmed chunk to a WAV staging directory and uses ffmpeg's concat demuxer to stream from those WAVs to the final MP3. Python holds one chunk's PCM at a time regardless of book length.

Silence trimming uses asymmetric thresholds: the leading edge uses -45 dBFS (fairly aggressive), the trailing edge uses -55 dBFS (softer). Finnish word-final unstressed vowels are quiet but not silent: a symmetric threshold that accurately removes leading silence over-trims the trailing edge and produces clipped-sounding word endings. The keep margins (30 ms leading, 100 ms trailing) ensure a small natural pad remains at each edge.

The old code also silently force-resampled chunks to match the first chunk's sample rate, channel count, and bit depth. If the first chunk was corrupt (wrong sample rate due to an engine bug), every subsequent chunk was dragged to that wrong format and the audiobook came out subtly wrong with no error. The replacement raises `AudioFormatMismatch` on any mismatch, surfacing engine-level bugs as early errors rather than silent format corruption.

## The English Grandmom Prosody Problem

Grandmom is the default voice character that emerges from the Finnish-NLP Chatterbox-Finnish finetune when called with no reference clip. Nobody recorded her. For Finnish synthesis this works cleanly. For English, the Finnish-only T3 finetune cannot be used; instead the multilingual Chatterbox base model is conditioned on a synthesized Grandmom reference clip (a short clip of Finnish Grandmom generated from the Finnish finetune and bundled at `assets/voices/grandmom_reference.wav`) to copy her vocal timbre.

The reference clip is Finnish speech. Chatterbox's reference conditioning copies more than timbre. It also partially copies the prosodic patterns of the reference language. Finnish sentence rhythm, particularly how short the pauses after terminal punctuation are, bleeds through into English output. The word "up" in sentence-final position is a documented specific failure: the model consistently slurs through the following period, sometimes hallucinating a filler token before the next sentence begins. Two separate synthesis runs (2026-05-17) confirmed the same failure shape with different following sentences, suggesting a word-level issue rather than random non-determinism.

The root cause is architectural, not a code bug: autoregressive neural TTS has no symbolic punctuation handling. Whether a period produces a pause is entirely a statistical property learned during training, not a rule. The workarounds available are raising `--chunk-chars` to keep text in one autoregressive run (eliminating chunk-boundary cold-start hallucinations), using ellipsis or em-dash instead of periods where prosody matters more than semantics, and re-rolling with `--overwrite fresh` to wipe the chunk cache and try again. Structural fixes (post-processing forced-alignment silence insertion, ASR validation with auto-reroll) would definitively solve the problem but are not yet built.

## The Finnish Normalizer: Sixteen Passes and Why

The Finnish normalizer runs before chunking so the chunker operates on fully expanded, correctly spelled text. All fifteen Finnish grammatical cases can be required on number words depending on context, and num2words alone cannot choose the right one. It only produces a given case when told which one to use. The governor-word detection approach (tracking ±3 tokens of context around each bare integer, matching against a table of governor words like "vuonna", "sivulla", "luvussa" to determine the required case) is the central design of pass G.

The pass order is load-bearing. Century expressions ("1500-luvulla") must be consumed before the bare-integer pass sees a loose "1500". Date patterns ("12.5.1905") must be consumed before the decimal pass sees "12.5". Abbreviations ("s. 42") must expand before the page-reference logic can derive the correct case for the following number. TOC dot-leaders ("..........142") must be stripped before the ellipsis pass turns them into spoken "dot dot dot dot".

The loanword lexicon (YAML, loaded once into a dict at import time) handles the Finnish pronunciation class that neither num2words nor any TTS engine handles correctly: words ending in "-ismi" (humanismi, rationalismi, liberalismi), Latin legal phrases (ius commune, ratio scripta), and German place names. The respellings in the lexicon are not IPA. They are Finnish orthography approximations that the target TTS engine produces correctly. "ius commune" respelled as "jus kommune" is not phonetically perfect; it is better than what an unassisted engine produces.

The English normalizer took a parallel architecture when English book support was added. Before v3.7, English books routed through the Finnish normalizer and received Finnish rules: Roman numerals were expanded as Finnish ordinals, number words got Finnish case inflection, and so on. The language dispatch fix routes each engine+language combination to the appropriate normalizer. The English normalizer's heavier passes (dates, telephone numbers, URLs, acronyms) live in standalone `src/_en_pass_*.py` files for isolated unit testing.

## GPU Exclusion Lock and Single-Instance Guard

Two concurrent Chatterbox or faster-whisper subprocesses allocate roughly 6 GB VRAM and 2 GB RAM each. On observed hardware, running two simultaneously swapped the GPU allocator into system RAM and froze the OS. The fix is an OS-level advisory lock in `src/process_lock.py`: `fcntl.flock` on POSIX, `msvcrt.locking` on Windows. The kernel drops the lock automatically if the holder crashes, so a dead run can never wedge subsequent runs: an important property because the voice-pack pipeline subprocesses (faster-whisper, pyannote) can crash without cleanup on some Windows configurations.

The single-instance guard in `src/single_instance.py` is separate: it prevents two GUI windows on the same machine (which would fight over chunk cache files and the synthesis output path). On Windows it acquires a named mutex; on other platforms it uses an `O_CREAT|O_EXCL` atomic lock file to avoid a race between two racing instances at startup. If the mutex is already held, a dialog asks whether to open a second window anyway with an explicit warning that GPU engines may conflict.

## Supply Chain Pinning

A rotating upstream URL or a force-pushed model repository can silently change what gets installed between two runs of the same workflow. v3.15.0 pinned every external fetch: HuggingFace model prefetch by commit hash, Piper voices by version, the Finnish T3 finetune by tag, and CI tooling (ffmpeg, pip, GitHub Actions) by SHA. The tessdata files for the OCR fallback are SHA-256-verified inline in the build workflow. The auto-updater verifies a SHA-256 hash before executing a downloaded installer; if the hash is absent from both the release notes and the `.exe.sha256` sidecar asset, silent install is blocked and the user is offered a manual browser download.

## Documentation Drift as a Recurring Bug Class

Three separate incidents of drift between two places that nothing compared mechanically led to the same class of fix each time: a check script that fails when the two disagree. `scripts/check_skill_catalog.py` verifies both directions of the skill directory versus README count. `scripts/render_cli_help.py` generates `docs/CLI.md` from argparse definitions and a pre-commit hook fails if the generated file differs from the committed one. `test_fi_v7_params.py` locks a production temperature constant to the value claimed in the architecture documentation. The pattern is consistent: the first time drift is noticed, fix it; the second time, write a check that fails loudly instead of waiting for a third instance to appear.
